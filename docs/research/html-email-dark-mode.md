# HTML email dark mode in AMC

24 November 2026. Background research from standards, browser source, client documentation, and published tests using synthetic mail.

## Approved behavior

The approved interaction is an on-demand appearance toggle beside each open HTML message's collapse chevron. Start with the existing original colors. The moon tries a dark background and the sun restores the original colors. Use the existing header row for the control. Keep the choice with the mounted message so the app's theme and other messages can be used independently.

The header and message body share local reader state. The existing sandboxed iframe applies and removes display styles in place, preserving the document, position, and image permissions. Keep the iframe preference light to avoid reactivating a partial sender stylesheet on an incompatible canvas. Recolor solid HTML surfaces and pair text with its local background where it can be determined. Keep the sender's colors over background images and gradients. The Electron smoke test covers keyboard activation, zero added body offset, restoration of sender colors, and remote image consent.

## Recommendation

Use the current sanitized light rendering as the baseline and make it reachable from an adapted message. The recommended default is to honor a usable sender dark theme, darken simple HTML whose colors AMC supplies, and use the baseline for uncertain layouts. If the goal is to darken image-heavy newsletters as well, make that broader conversion opt-in with a per-message way back.

A message can declare a supported scheme, contain rules for the preferred scheme, and still be unreadable after the cascade and client transformations. A client can also darken a message with no sender support at all. There is no basis here to assume most incoming mail supplies a usable explicit dark version. Compatibility tables measure whether tested clients honor constructs. Client share measures reader software usage, and fixture suites measure behavior on selected inputs. Measuring author adoption would require a representative corpus of delivered HTML, a defined denominator, and separate counts for declarations, effective visual changes, and readable output after sanitization. No mailbox prevalence was measured. [Can I email feature tests](https://www.caniemail.com/features/css-at-media-prefers-color-scheme/) · [MailSlurp test methodology](https://www.mailslurp.com/guides/email-client-support-report/)

## What sender signals establish

| Signal | What it establishes | How to verify |
| --- | --- | --- |
| `<meta name="color-scheme" content="light dark">` or a winning root `color-scheme: light dark` declaration | The sender declares that the document can use both schemes. The scheme determines browser defaults such as canvas, default text, controls, and scrollbars. Metadata can inform the early paint before CSS loads. The declaration alone provides no paired custom text and background colors. The CSS property can also be scoped to a subtree. | Check the retained metadata, winning property at the root and on scoped elements, and painted default and explicitly colored regions. A logo with an explicit fill and a text run with an explicit color can still fail when the default canvas changes. [HTML metadata](https://html.spec.whatwg.org/multipage/semantics.html#meta-color-scheme) · [CSS Color Adjustment](https://www.w3.org/TR/css-color-adjust-1/#color-scheme-prop) |
| `@media (prefers-color-scheme: dark)`, a conditional stylesheet or image source, or `light-dark()` | A media query selects CSS or resources according to the rendering preference. The `light-dark()` function selects a value according to the element's used scheme. A dark rule might affect one link, match no retained node, lose to an inline declaration, or apply only at one width. A message authored in dark colors can lack every one of these signals. | Check active queries and actual changed regions in the sanitized frame, across both schemes and supported widths. Include a one-rule message, a losing rule, and a dark-by-design message. [Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#prefers-color-scheme) · [CSS Color 5](https://www.w3.org/TR/css-color-5/#light-dark) |
| `color-scheme: light only` or `content="light only"` | The author requests a light used scheme and blocks the specification's color-scheme override on that element. The property does not set the media query's preference in the same document. A mail client can apply its own policy to delivered HTML. | Separate the CSS property from the HTML metadata and test browser auto-darkening independently of the preference. Can I email's September 2026 metadata tests mark Gmail iOS and Android as partial for the literal `light only`, with desktop and mobile webmail marked unsupported. That result says nothing about Gmail honoring `light dark` or the dark media query. [CSS override rules](https://www.w3.org/TR/css-color-adjust-1/#color-scheme-override) · [Can I email metadata results and fixture](https://www.caniemail.com/features/html-meta-color-scheme/) |
| `supported-color-schemes` and Outlook selectors such as `[data-ogsc]` and `[data-ogsb]` | The former is historical WebKit syntax. The latter target attributes emitted by some Outlook rendering paths. Their presence is evidence of client targeting, with behavior tied to the software that supplies those attributes. | Test these separately from standard constructs. Keep legacy and vendor-only fixtures in the corpus so classification does not treat them as proof of an effective Chromium dark palette. [WebKit on the rename and Mail](https://webkit.org/blog/8840/dark-mode-support-in-webkit/) · [Litmus Outlook experiments](https://www.litmus.com/blog/the-ultimate-guide-to-dark-mode-for-email-marketers) · [MailSlurp Outlook Android results](https://www.mailslurp.com/guides/email-client-support-report/#dark-mode) |

## Chromium and the pitfalls of automatic darkening

Electron's `nativeTheme.themeSource` changes Chromium's reported scheme preference as well as native UI appearance. Blink has a distinct force-dark setting. Its source also has an embedding path that can supply the iframe owner's preferred scheme to the child. The CSSWG working draft explicitly specifies preference propagation for a class of embedded SVGs and still discusses iframes. Verify the supported Electron build's actual behavior for the intended iframe configuration. In particular, check the child's media query, the document canvas, and the surrounding app independently. Setting the child root's supported scheme and changing the preference it sees are separate operations. [Electron nativeTheme](https://www.electronjs.org/docs/latest/api/native-theme#nativethemethemesource) · [Blink iframe preference and force-dark setting](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/core/css/style_engine.cc#L4627-L4640) · [Blink embedding scheme resolution](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/core/css/style_engine.cc#L4839-L4851) · [Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#prefers-color-scheme)

Chromium's filter uses separate foreground and background classifiers, a lightness transform, and role-specific corrections for borders and selection. Image handling has its own policy and pixel classifier, with inputs such as transparency, luminance, and color distribution. That helps explain why an engine can keep some photos and recolor some graphics. A classifier has no author-provided meaning for a logo, chart, or status color and can make the wrong choice. The source is an upstream snapshot. Verify both behavior and scope on the Electron build before treating a browser switch or experimental DevTools command as a per-message control. Use rendered pixels as well as CSS values, because the filter operates on paint flags. [Blink paint filter](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/platform/graphics/dark_mode_filter.cc#L142-L289) · [Lightness transform](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/platform/graphics/dark_mode_color_filter.cc#L24-L66) · [Image classifier](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/platform/graphics/dark_mode_image_classifier.cc#L328-L419) · [DevTools automatic dark-mode override](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setAutoDarkModeOverride)

- **Contrast is a property of the final foreground and its actual backdrop.** An element with a transparent background can sit over an ancestor's table cell, a gradient, or an image. Opacity and layering can change the result again. Transforming the foreground and background independently can make formerly readable text, links, separators, or selected text disappear. Recoloring only one half of a pair can fail too, as observed in the iPhone fixture with dark CSS. [CSS canvas rules](https://www.w3.org/TR/css-color-adjust-1/#color-scheme-effect) · [Compositing and Blending](https://www.w3.org/TR/compositing-1/#simplealphacompositing) · [iPhone fixture](https://www.mailslurp.com/guides/email-client-support/apple-mail-dark-mode/)
- **Image exemptions have two failure modes.** Leaving a transparent black wordmark alone can hide it against a dark replacement surface. Inverting the whole document can alter product photos, screenshots, QR codes, and the colors of image-based status indicators. Applying a second filter to an `img` cannot generally restore CSS backgrounds, inline artwork, or the original interaction of alpha with the backdrop. [Filter Effects](https://www.w3.org/TR/filter-effects-1/#funcdef-filter-invert) · [Blink image filtering](https://github.com/chromium/chromium/blob/23d777a6388046f8eacc8415343a4ba016fa1314/third_party/blink/renderer/platform/graphics/dark_mode_filter.cc#L197-L245)
- **A CSS rewrite has to preserve the cascade and authored meaning.** Inline rules, `!important`, inherited colors, custom properties, conditional rules, table `bgcolor`, and quoted sections can all affect the paint. The same color token can serve as body text in one place and a semantic status fill in another. Classifying on raw HTML strings misses those distinctions. Changing the preference and running a recolorer can also alter an already-effective author palette or trigger different conditional resources. [CSS Cascade](https://www.w3.org/TR/css-cascade-5/#cascade) · [HTML rendering rules](https://html.spec.whatwg.org/multipage/rendering.html#tables-2) · [Outlook Android fixture](https://www.mailslurp.com/guides/email-client-support-report/#dark-mode)

## Options for AMC

| Option | Tradeoff | Decision criterion |
| --- | --- | --- |
| A. Sender dark mode only | Uses effective sender styles and assets as delivered. Mail with absent or uncertain dark styling gets the current light rendering. This can leave many newsletters bright. | Compare complete, partial, and absent author-mode fixtures. Check for a real palette change, paired readable foreground and background colors, and immediate access to the original appearance. |
| B. Sender dark mode and simple email | Adds a dark canvas and matching text for HTML whose colors AMC supplies. Explicitly styled layouts still need a usable sender theme to switch automatically. This is the closest match to Apple's documented design for simple and rich email. [Apple's mail dark-mode design](https://developer.apple.com/videos/play/wwdc2019/511/) | Verify eligibility with nested quotes, links, inline colors, fixed table cells, and transparent logos. Require readable app-managed colors and fall back when the actual backdrop is ambiguous. |
| C. Darken styled mail on request | Builds on B with an optional dark conversion for newsletters and other authored layouts. Can reduce more glare, with greater risk of altered brand colors, hidden logos, and weaker contrast. | Compare a scoped browser mechanism and AMC-controlled recoloring on the same corpus. Require per-message isolation and a reliable return to the original. Treat whole-frame inversion as a comparison fixture for color damage. |

Here, **original appearance** means the regular sanitized HTML in the baseline light preference with AMC recoloring disabled. It preserves the sender's authored styles and layout, including deliberately dark designs. Raw message source, plain text, and remote-image permission are separate reader actions.

## Verification

1. **Test each signal in isolation before combining them.** Include unstyled HTML, inline-only mail, metadata-only support, root and scoped `color-scheme`, `light only` via both paths, full and incomplete dark CSS, vendor selectors, already-dark mail, and a query that matches only at some reader widths. Use the same document with one variable changed to test causation. Exercise supported and stripped signals through the real sanitized document path.
2. **Test the painted result.** Use nested transparent tables, `bgcolor`, gradients and background images, links and selection, colored status cells, light and dark transparent logos, screenshots, photographs, and a QR code. Record both rendered screenshots and computed styles or sample pixels. Check normal text against a 4.5:1 contrast target and large text against 3:1 for app-managed colors, with 3:1 for applicable control boundaries and meaningful graphics. Compare arbitrary sender styles to the baseline and flag regressions and ambiguous backdrops for visual review. [WCAG 2.2 text contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum) · [Non-text contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast)
3. **Exercise mode changes in the reader.** Use an isolated Electron profile with synthetic mail. Cover light and dark initial paint, system and app theme changes, messages with different appearances in the same thread, repeated toggles, and switching threads. Check keyboard access and visible state of the recovery control, scroll and focus continuity, and the absence of a bright flash. With blocked, permitted, delayed, and failed images, verify that either view retains the message's request policy and existing navigation protections.
4. **Record the scope of every result.** For AMC record Electron and Chromium versions, OS, frame mode, and fixture. For external comparisons use the same delivered synthetic MIME in both modes, record the client build and account type, and vary one declaration at a time. Track author-mode success, usable fallback, and visible regressions per fixture. A corpus built to expose failures cannot estimate mailbox prevalence.

## AMC feedback and reproduction

The AMC 0.1.1 capture at commit `994727a6a8a5` shows a dark inbox and a white HTML newsletter in the reader. The latest entry in the supplied error excerpt predates the capture by about six minutes. The rendering policy accounts for the symptom. The capture establishes the displayed colors. The original message's support for dark mode is unknown.

AMC sets the iframe to `color-scheme: only light`, inserts its own `only light` metadata in the sanitized document, and provides an explicit white root background and dark text. Sanitization strips all sender `meta` tags while permitted style blocks survive. The explicit iframe scheme was added after preserving sender head styles exposed a contrast regression. A sender rule turned text light while AMC's canvas stayed white. The regression fixture still asserts that dark-mode media rules stay inactive and an explicitly styled dark card keeps its sender colors. `pnpm test:html-reader` passed on the current checkout, `5d09196`, with Chromium `156.0.8078.100`. A separate temporary Electron probe used the current sanitizer and document builder in a sandboxed iframe, then changed only the outer iframe's scheme from `only light` to `dark`. The probe held AMC's inner metadata and base CSS constant and kept the same document in all cases.

| Synthetic message | What Chromium did when the iframe requested dark |
| --- | --- |
| Sender sets body background and text together in a dark media rule | The query matched and the message body switched to `#eee` on `#191919`. Contrast was 15.15:1. The explicitly white root still computed as white. |
| Sender sets only text to white in a dark media rule | The query matched and produced white text on the existing white canvas, at 1:1 contrast. |
| Sender fixes the colors inline | The query matched and the sender's `#222` on `#fff` stayed in place. |
| Sender supplies only a `light dark` meta declaration | Sanitization removed the declaration. The text and canvas remained `#1f1f1f` on `#fff`. |
| Simple HTML uses AMC defaults | The query matched and AMC's explicit colors remained `#1f1f1f` on `#fff`. |

The probe isolates scheme negotiation. A selected policy still needs Electron checks for the final painted canvas, layout and image behavior. A fixture with white-on-white text would prevent a regression to plain theme inheritance. Normal-size text on known solid backgrounds can use WCAG's 4.5:1 minimum as a test criterion. Gradients, overlapping layers and images require rendered checks. [WCAG contrast criterion](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

For the selected approach, test authored light and dark variants, partial rules, plain HTML, quoted replies, nested table and inline colors, already-dark regions, transparent logos, and image-heavy newsletters with blocked and allowed images. Check the first visible frame, theme changes, the message's scroll position and focus, and existing image request policy. This research made no changes to application code.

### Chromium automatic darkening probe

In a second isolated Electron window on Chromium `156.0.8078.100`, enabling the DevTools auto-dark override via the parent web contents changed the sampled white background pixels from `#fff` to `#121212` in the parent and in two synthetic message iframes. One iframe and document declared `light`, the other `only light`. This tests the effect of that specific emulation command from the top-level target. It establishes that this invocation affects the host as well as the messages. A per-message conversion would need a scoped mechanism and independently verified control over the original view.
