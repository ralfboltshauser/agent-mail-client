# Incoming HTML email rendering in AMC

23 November 2026. AMC document probes used `d92a9c5`. The follow-up rechecked the current reader and tested keyboard scrolling in an isolated iframe. The investigation changed no application code.

## Recommendation

Keep Chromium, DOMPurify, and the sandboxed iframe. Rework the incoming HTML renderer around three responsibilities: assemble one structurally correct message document, let the sender's layout run with minimal app styling, and give the reader a reliable way to read content that genuinely exceeds the viewport. Test the resulting behavior with a synthetic compatibility corpus in Electron.

A 780 px table with a 780 px minimum cannot fit into 320 px while retaining its dimensions, keeping text at its original size, and showing everything at once. Every renderer must allow scrolling, change the layout, scale the document, or lose content. The desktop default should prioritize legible text and access to every column. Provide horizontal scrolling for genuinely wide layouts. A wider reading area and a text view are separate recovery options for a later delivery. Retain sender-authored media queries so messages that can reflow do so first.

## What AMC does today

1. [Engine returns stored HTML](../../apps/engine/src/http/mail.ts#L314). [Desktop main caches it](../../apps/desktop/src/main/index.ts#L876). The [reader resolves supported CID image references](../../apps/desktop/src/renderer/src/features/thread-reader/message-content.tsx#L61) before it mounts the HTML body.
2. [Message document construction](../../apps/desktop/src/renderer/src/components/html-message-document.ts#L17) sanitizes in whole-document mode, serializes the sanitized root, and concatenates that root inside another document's body. The wrapper adds a CSP and stylesheet. That stylesheet governs word breaking, table and media widths, image sizing, preformatted whitespace, body padding and typography, links, and quotes.
3. [The iframe adapter](../../apps/desktop/src/renderer/src/components/message-body.tsx#L25) sets `srcdoc`, observes and measures the body to set the frame height, and routes clicks and keyboard events. The [reader shell](../../apps/desktop/src/renderer/src/components/thread-view.tsx#L59) separately constrains the available width. [Existing reader tests](../../apps/desktop/src/renderer/src/components/thread-view.test.ts#L1) use jsdom, whose upstream documentation explicitly says it does no visual layout. [jsdom rendering limits](https://github.com/jsdom/jsdom#pretending-to-be-a-visual-browser)

These are three independent sources of behavior. A layout complaint can come from authored HTML, AMC's transformations, or the interaction between a well-formed message and the width offered by the reader.

## What Electron showed

I ran a hidden Electron window on Chromium `156.0.8078.100` with the current AMC sanitizer, document builder and iframe sandbox on synthetic HTML. Frame widths were 623 and 320 CSS px. I measured text line counts with `Range.getClientRects()`, and horizontal overflow as the iframe document's scroll width minus its client width. A separate document-assembly probe inserted the same AMC head nodes at the start of the sanitized document's actual head before serializing that single root. This exercised the document and Chromium layout seam in isolation from the mounted production reader.

| Synthetic fixture | AMC today | What the probe established |
| --- | --- | --- |
| CI-style data table | Status spans six lines at both widths. The table is 512 px wide at 623 px. | Restoring the word's intrinsic width on headers gives one line at both widths. The table remains 512 px at 623 px. |
| Same table with a 180-character token in a body cell | The token wraps within a table with zero horizontal overflow. | Minimal CSS also restores Status but the table expands to about 2,608 px, overflowing the 623 px frame by about 2,025 px. Keeping emergency wrapping in the body cells avoids that expansion in this fixture. |
| 780 px table with a 780 px minimum | It already overflows by 177 px at a 623 px frame even with AMC's global table cap. | The right edge was reachable via programmatic scrolling. Discoverability, keyboard behavior, and the horizontal scrollbar's availability inside the mounted reader remain unverified. |
| Responsive two-column layout with a stylesheet in the head | Cells stay side by side at 623 px and stack at 320 px. | Head style relocation does not break every rule. Width-based media queries use the iframe viewport. [Viewport behavior](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/CSSOM_view/Viewport_concepts) |
| A stylesheet targeting the first body element | The parser places the sender's head stylesheet inside the body ahead of the content. Its `body > .probe-content:first-child` rule misses. | With one document and the same AMC defaults, the stylesheet stays in the head and the rule applies. This is independent of wrapping. [HTML parser rules](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inbody) |
| Image with 120 × 120 dimensions in HTML and a 200 × 100 intrinsic image | The displayed size is 120 × 60. | Minimal CSS restores the dimensions from the markup. The global image defaults can protect fluid layouts and also override deliberately specified geometry. |
| Long unbroken paragraph and preformatted line | Current defaults wrap both in the tested frame. | Minimal CSS alone introduces horizontal overflow for both. Preformatted text needs an explicit decision about preserving lines and making them reachable. |

The CI example exposes an intrinsic-sizing conflict. `overflow-wrap: anywhere` contributes emergency breaks to min-content sizing. `break-word` still permits an emergency break in a constrained line, but those break points do not reduce min-content width. This distinction also applies to other elements that participate in intrinsic sizing. A previous probe found that applying `break-word` to every table header can itself widen a table with an unusually long unbroken heading. Neither a global rule nor geometry alone can tell us whether a visually cramped document is correct. The six-line heading fits the viewport and reports zero overflow. [CSS Text specification](https://www.w3.org/TR/css-text-3/#overflow-wrap-property) · [CSS table sizing](https://www.w3.org/TR/css-tables-3/#table-layout) · [Web Platform Tests for the two wrap values](https://github.com/web-platform-tests/wpt/tree/master/css/css-text/overflow-wrap)

### A scrollable width can still be unreachable

A follow-up Electron probe used a 780 px table in a 320 px iframe and sent a Chromium keyboard event to the focused message. With native horizontal scrolling, Arrow Right moved the viewport 40 px. With sender `html { overflow-x: hidden }`, it moved 0 px, even though the document still reported 460 px of overflow and JavaScript could scroll the entire 460 px. An app-owned root overflow override restored keyboard movement. An RTL version moved 40 px left with Arrow Left. With a classic scrollbar, the usable viewport height was 15 px less than the iframe height in this environment. These are isolated document results. The full reader's focus entry, pointer behavior, and last-line reachability need their own tests. [CSS Overflow definitions](https://www.w3.org/TR/css-overflow-3/#overflow-properties)

### Auto-height can have no stable answer

A follow-up Chromium probe repeatedly applied AMC's current height rule to a synthetic message whose content was 300 px tall below a 200 px iframe viewport and 120 px tall above it. An initial 120 px viewport produced 302 px, then 122 px, then 302 px again. This probe manually applied the sizing rule in an isolated frame. It establishes that a stable auto-height cannot be assumed for arbitrary sender CSS. [Current measurement](../../apps/desktop/src/renderer/src/components/message-body.tsx#L43-L52)

None of the libraries examined supplies an installable renderer with AMC's fidelity, viewport, and privacy requirements. The renderer AMC already has, Chromium, performs the layout. The part AMC needs to own is the policy around that layout.

## Implementation plan

Keep the first delivery to the desktop HTML reader. Land a real-browser harness, valid document assembly, a usable viewport, and a tested wrapping policy. Keep new recovery UI, CSS parsing, and mailbox-wide state changes out of this delivery.

1. **Start with two verification paths.** Extend the existing dev-only mail fixture with HTML and attachment-backed images. It currently returns plain text and bypasses preload, so run the full reader in a fresh Electron development profile for layout and input. Capture the existing Status, head-order, and hidden-overflow failures before editing production code. Measure the actual iframe width at the 900 px minimum AMC window and at ordinary and expanded widths. Keep 320 and 623 px as reproducible document-level probe widths. For request and sandbox checks, use a separate Electron integration check with the actual parent CSP and main-process request filter, and a controlled loopback endpoint with a request counter. Use the existing jsdom harness for React commits and continuity. Add the deterministic Electron checks to Linux CI using a virtual display and validate scrollbar modes and trackpad input on macOS. Run `pnpm check` and `pnpm build`. [Dev fixture entry](../../apps/desktop/src/renderer/src/main.tsx#L10-L17) · [Fixture data](../../apps/desktop/src/renderer/src/dev/mail-fixture.ts) · [Parent CSP](../../apps/desktop/src/renderer/index.html) · [Session request policy](../../apps/desktop/src/main/message-image-requests.ts) · [CI](../../.github/workflows/ci.yml)
2. **Fix document assembly with the current stylesheet.** The document builder should own sanitization, insertion of AMC's early CSP and defaults, and serialization of one document. Preserve sanitized root and body attributes, permitted head style order, and direct body-child relationships. Keep `about:srcdoc`, the frame sandbox, remote-image policy, CID resolution, and external link routing. Check zero image requests before consent, the expected message-image request after consent, and zero remote image requests from the parent renderer. The head-order fixture should go green in this step. [Document builder](../../apps/desktop/src/renderer/src/components/html-message-document.ts)
3. **Give the iframe viewport ownership of horizontal scrolling and `HtmlBody` ownership of its measured height and overflow state.** Keep the outer reader's vertical scroll and the iframe at its container width. Enforce scrolling at the document viewport, including conflicts with sender root or body overflow declarations, and leave sender-defined inner layout alone. Reuse native scrolling and show a visible, keyboard-reachable affordance for overflowing messages even with overlay scrollbars. A fitting message should gain no extra tab stop. Reserve actual scrollbar space and verify the bottom line. Recheck after frame load, reader resize, and relevant image load or failure. Batch measurement and skip unchanged geometry. Detect recurring height values or repeated sizing churn within one layout pass. In that exceptional case, use a stable, bounded viewport with native vertical scrolling so content remains reachable. Retry auto-sizing on an external change such as a new document or reader resize. Avoid rewriting `srcdoc` for geometry changes. [Existing iframe lifecycle](../../apps/desktop/src/renderer/src/components/message-body.tsx#L25-L83) · [Resize Observer](https://www.w3.org/TR/resize-observer/) · [Proton height-query handling](https://github.com/ProtonMail/WebClients/blob/d3c29acc8de2e14a1ee4ef4b7d2d3fd6c4b78077/packages/mail-renderer/src/helpers/transforms/transformStylesheet.ts#L51-L107)
4. **Choose wrapping defaults after containment works.** Start by testing `break-word` against the existing `anywhere` behavior. Use the fixtures to determine where narrower rules are necessary. The short heading must remain one line when it fits. The existing long-identifier table and ordinary prose must remain readable without horizontal travel at the widths where they currently fit. A separate fixed-width invoice should retain its column geometry and scroll. Preserve declared dimensions for fitting images and check oversized images and preformatted lines for reachability. Evaluate these changes by structure so fixes apply across senders. [CSS Text specification](https://www.w3.org/TR/css-text-3/#overflow-wrap-property)

### Release gates

| Case | Observable result |
| --- | --- |
| Intrinsic layout | Status occupies one line at 320 and 623 px in the known fixture. The long-token fixture has no horizontal overflow at either width and the token stays fully readable. Ordinary prose reflows without horizontal travel. |
| Sender structure | The first-child and responsive rules apply. The fitting image retains authored dimensions. Nested tables, spanning cells, and RTL preserve reading order. |
| Genuine overflow | Starting in the mounted reader, keyboard and trackpad can reach the end column and bottom line at actual size, including RTL and sender-hidden overflow. Root and body CSS fixtures cover inline `!important`. The last focusable link stays reachable with classic and overlay scrollbars. Focus can return to the reader and vertical scrolling in multi-message threads remains usable. Geometry and programmatic scrolling alone are insufficient. |
| Dynamic geometry | A narrow-to-wide resize and delayed or failed images settle. Resize preserves iframe identity, focus and selection for the same document, and height can shrink again. The two-height fixture reaches the bounded fallback without clipping content or continuing to resize. A no-op mailbox refresh leaves the iframe document in place. [Desktop React baseline](../desktop-react-audit.md) |
| Request behavior | The controlled endpoint observes zero requests before consent and the expected image request after consent. The parent renderer still cannot fetch remote images. CID images and external link handling preserve current behavior. |

### Follow-up scope

Evaluate a genuinely wider reading pane or a per-message plain-text action after the first delivery. AMC's current expanded reader still uses the same `48rem` cap. Plain text should use the existing body path and remain an explicit choice. Consider opt-in scale-to-fit if actual-size reading remains awkward on narrow readers.
