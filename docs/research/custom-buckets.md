## How Buckets work

1. **Definitions.** The shared protocol exports seven names in a fixed order: Reply, Action, Follow-up, Update, Later, When I have time, and Newsletters. That array feeds a Zod enum. Each name maps to a separate fixed decision-log ID such as `bucket.follow_up`. The assignment and write schemas use the name enum. Model predictions use the decision-label enum. `bucket.clear` is a recorded decision and clearing the assignment stores `NULL`. [Bucket protocol](../../packages/protocol/src/buckets.ts#L5), [decision labels](../../packages/protocol/src/decision-labels.ts#L4), [clear handling](../../apps/engine/src/mail/triage/corrections.ts#L199)
2. **Storage.** The Engine owns one nullable Bucket per account-scoped Thread. SQLite stores the display name in `thread.bucket TEXT` alongside the reason, setter, and timestamp. The SQL column itself accepts text. The API and model contracts enforce the list. The store updates the Thread and emits a replica change. A Bucket assignment has no Gmail or IMAP writeback. Provider Labels and folders are represented through their own data and operations. [Thread schema](../../apps/engine/src/db/migrations.ts#L89), [Bucket columns](../../apps/engine/src/db/migrations.ts#L486), [assignment write](../../apps/engine/src/mail/store.ts#L110), [Label sync](../../apps/engine/src/mail/store.ts#L131)
3. **Manual assignment and review.** Desktop sends the assignment through IPC to `PUT /v1/bucket`. The HTTP route validates the Bucket and dispatches owner, review, or scoped agent writes. The CLI's `amc bucket` command resolves a name from the enum and also accepts `clear`. MCP exposes `set_bucket` with the same assignment schema. Owner review records the decision, checks the Thread or reviewed input revision, and supports Undo. [Desktop IPC](../../apps/desktop/src/main/index.ts#L631), [HTTP route](../../apps/engine/src/http/buckets.ts#L12), [CLI](../../apps/cli/src/main.ts#L483), [MCP](../../apps/engine/src/mcp/server.ts#L155), [review and Undo](../../apps/engine/src/mail/triage/corrections.ts#L90)
4. **Automatic triage.** The broker reads eligible untriaged Inbox Threads and gives the model a prompt with the current Bucket meanings and a JSON schema derived from the protocol. The Engine maps the returned decision ID to a Bucket name and applies it only while the captured input is current and the Thread remains eligible with an empty Bucket. The same run can also record a Filter suggestion. Applying Filter changes provider placement through a separate path. [Broker](../../apps/cli/src/triage.ts#L346), [prompt](../../apps/cli/prompts/triage.md#L5), [Engine projection](../../apps/engine/src/mail/triage/model.ts#L303), [Filter targets](../../apps/engine/src/mail/triage/filtering.ts#L142)
5. **Desktop views.** The sidebar, picker, command palette, and review choices read the fixed array. The picker and review also derive number shortcuts from its order. The replica selects and counts Threads by their stored assignment, with no Inbox condition on the Bucket view. The sectioned Inbox has separate rules. New senders take precedence, Reply and Action share **Action/Reply**, Follow-up has its own section, and the remaining Threads go to **Other mail** or **Seen** based on read and handling state. A Bucket view therefore has a different membership rule from an Inbox section. [Sidebar](../../apps/desktop/src/renderer/src/components/app-sidebar.tsx#L265), [picker](../../apps/desktop/src/renderer/src/components/bucket-picker.tsx#L45), [palette](../../apps/desktop/src/renderer/src/components/command-palette.tsx#L200), [review choices](../../apps/desktop/src/renderer/src/features/triage-review/review-card.tsx#L141), [replica filter](../../apps/desktop/src/main/replica.ts#L386), [replica counts](../../apps/desktop/src/main/replica.ts#L486), [section logic](../../apps/desktop/src/renderer/src/data/thread-queries.ts#L122), [section label](../../apps/desktop/src/renderer/src/features/thread-list/inbox-chrome.tsx#L73)

## What owner-created Buckets would change

The first product choice is whether a custom Bucket is a destination the owner can assign manually, whether automatic triage may also assign it, and where it appears. These choices reach different code paths.

- **Manual assignment** would need Engine-owned definitions and a stable ID so renaming the display name preserves assignments and history. The current name-based protocol, assignment reads and writes, and Desktop choices would all need to accept those definitions. Account scope and what deleting a definition does to assigned Threads and Undo are open decisions.
- **Automatic assignment** would also need each eligible definition and its meaning in the triage context, plus validation of emitted IDs against that context. Today the prompt and output schema ship with the app and the Engine resolves an ID through the fixed map. [Prompt and schema selection](../../apps/cli/src/triage.ts#L363), [Engine mapping](../../apps/engine/src/mail/triage/model.ts#L312)
- **A sidebar destination** can build on the existing assignment-based replica filter. **A dedicated Inbox section** would additionally change the Inbox routing rules and require a decision about ordering and behavior alongside New senders, Action/Reply, Follow-up, Other mail, and Seen. [Replica filter](../../apps/desktop/src/main/replica.ts#L386), [Inbox routing](../../apps/desktop/src/renderer/src/data/thread-queries.ts#L122)
